Preview Markdown without executing author HTML

A technical writing interface should display code, headings and lists clearly. But the article being typed is untrusted input. This is how we added a deliberately limited Markdown preview to the 24GOTOP Draft Lab without interpreting arbitrary HTML.

24GOTOP engineering · Implementation PR #40 · Regression tests

Scope: this is a static, browser-only experiment. It cannot register users, publish to the network, or create permanent article URLs. A green unit-test suite is not an external security certification.

Why even a preview deserves a threat model

Draft Lab originally inserted the article body as plain text. That kept hostile markup inert, but it made writing code-oriented articles harder to review. The naive alternative—taking user-controlled Markdown, treating it as HTML and assigning it to innerHTML—could turn a preview into an injection surface.

Consider an example article about unsafe image handlers. The author may intentionally type markup resembling an HTML image tag with an event handler, or a fenced code sample that contains script tags. Those bytes are valid documentation. They should neither disappear nor become executable UI.

Our scope was therefore narrower than “implement all Markdown.” We aimed to visually distinguish the blocks authors use most, while preserving the original text for export and avoiding new network or persistence paths.

The implementation: explicit tags, literal content

In PR #40, the new preview module separates two operations. First, a small parser recognizes headings, paragraphs, lists, block quotes, horizontal rules and fenced code. Second, a renderer creates only a fixed set of ordinary DOM elements and assigns author-controlled strings through textContent.

const paragraph = document.createElement('p');
paragraph.textContent = authorText;
container.replaceChildren(paragraph);

For a fenced block, the renderer creates pre and code elements, then assigns the code sample as text. For headings, it uses lower-level headings beneath the article title to avoid breaking the page's heading hierarchy. A small amount of CSS keeps code blocks scrollable within mobile layouts.

At the time of PR #40, the renderer did not create interactive Markdown links: no Markdown-provided tag, attribute, URL or event handler was used. That baseline was intentionally narrower than full CommonMark. Update, 30 October 2026: PR #78 subsequently introduced a bounded HTTP(S) citation-link syntax with a separate URL validator and fixed DOM-only anchor construction. Arbitrary raw HTML, image embeds, scripts and unsupported Markdown are still inert. Read the later security analysis for the new trust boundary.

What the tests actually prove

The Node tests exercise headings, paragraphs, ordered and unordered lists, blockquotes, code fences and unclosed fences. They also pass HTML-like strings into the renderer and assert that the created node types are restricted and the suspicious markup remains in textContent.

We retained the earlier Draft Lab import/export format: a writer can download a Markdown file, leave the tab and reopen that file later. The preview does not silently upload, save or normalize away the body of the original article.

Developers can reproduce the source checks locally with Node.js 22 or newer:

git clone https://github.com/rf24kja/24GO.top.git
cd 24GO.top
npm run check
npm test

GitHub Actions succeeded on PR #40. These are automated source-level checks. We have not yet completed independent screen-reader, real-device or public-URL verification for the latest editor.

Trade-offs and what we deliberately did not build

  • Not a full Markdown engine: inline emphasis, link rendering, nested lists, tables and syntax highlighting are not implemented. Unknown syntax stays visible as text.
  • Not a production content renderer: real published articles still need a reviewed Markdown pipeline, explicit content security policy, URL rules, attribution and moderation.
  • No draft durability unless the user exports: the preview runs locally. Closing or refreshing the tab loses unsaved text.
  • No measured adoption claim: unit tests do not tell us whether authors prefer this interface. That requires consenting volunteers and clear task results.

Review the code, not the hype

We would value a review of the parser edge cases, mobile code overflow, keyboard behavior and accessible semantics. The Draft Lab user pilot still needs real independent participants; the staging security test plan concerns the separate authenticated publishing backend. Neither is marked complete by the preview PR.

Which single code-oriented writing feature should we validate next: inline formatting, citations, syntax highlighting or an explicit Markdown source/preview switch? Bring a small reproducible case to the publishing RFC or the GitHub Discussions.

Evidence: merged PR #40, change log and module readiness register. This article describes source implementation and known limitations, not a launched hosted product.
