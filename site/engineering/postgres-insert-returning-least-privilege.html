INSERT succeeds, RETURNING fails: a least-privilege lesson

A database test can fail for the right reason. When we exercised a tightly scoped insert-only role in disposable PostgreSQL 17 CI, a convenient RETURNING clause requested a permission the role was deliberately designed not to have.

24GOTOP engineering · Official PostgreSQL 17 INSERT reference · Public security test plan #38

Scope: this is a general reproducible PostgreSQL permission lesson, inspired by a disposable CI test while designing a private, unreleased article-storage candidate. It is not evidence that 24GOTOP public article publishing or moderator identity checks are live. No private database SQL, credentials or provider records are published here.

One SQL statement, two different privileges

PostgreSQL supports grants scoped to particular columns. If a role may insert an article body but must not read back other database rows, blanket GRANT INSERT, SELECT ON table is unnecessarily powerful.

The difference becomes visible in an intentionally simplified example. Assume a dedicated, unprivileged role has only the column grant shown below and no general read permission:

GRANT INSERT (body) ON example_notes TO example_writer;

-- Write-only attempt:
INSERT INTO example_notes (body) VALUES ('A test note');

-- Different access requirement:
INSERT INTO example_notes (body) VALUES ('Another note')
RETURNING id;

The second statement asks PostgreSQL to return id from the affected row. That requires SELECT permission on the referenced column in addition to the relevant INSERT permission. Depending on row-level security configuration, a SELECT policy may also be necessary. PostgreSQL's INSERT documentation explicitly distinguishes these permissions.

The tempting fix is often the wrong fix

Granting broad SELECT merely to make a test assertion pass would change the application's security model. The role is meant to write, not inspect the table. A test demanding more authority than the feature requires is a test-design problem, not necessarily an application defect.

In our disposable test, we removed RETURNING and checked the INSERT command's row count. An independent, privileged CI fixture then inspected the saved row and compared it with the intended immutable source. We did not give the write-only role the ability to read the published-body table.

That separation does not make a role magically secure. It still requires role membership checks, a non-bypassable RLS policy, constraints, a controlled connection, and realistic failure tests.

Test effective privileges, not just grants that look right

Another useful PostgreSQL distinction: table-wide INSERT and per-column INSERT rights are not interchangeable in catalog probes. A column-limited role may have permission to write body without passing a table-wide privilege check.

SELECT has_table_privilege(
  'example_writer', 'example_notes', 'INSERT');

SELECT has_column_privilege(
  'example_writer', 'example_notes', 'body', 'INSERT');

Tests should check the effective permission needed by the SQL statement, explicitly assert that forbidden columns remain inaccessible, and try negative operations as a non-superuser. In addition, RLS with FORCE ROW LEVEL SECURITY is valuable defense in depth but does not replace grants or identity verification.

A practical review checklist

  1. Write down whether the runtime role is supposed to read, create, update or delete each field.
  2. Check effective table- and column-level privileges; include prohibited operations and role membership.
  3. Exercise real SQL as an isolated non-superuser, including INSERT ... RETURNING and duplicate-key failures where relevant.
  4. When a test fails, inspect the exact denied privilege before expanding production grants.
  5. Keep privileged verification fixtures and untrusted runtime requests separate; neither a DBA simulation nor a mocked JWT proves real user authorization.
  6. Do not expose a public article API until moderator identity, atomic state transitions, safe rendering, takedowns and backups have been validated end to end.

Try the public project and review the assumptions

The 24GOTOP open-source repository contains a local, early-stage publishing prototype, an experimental SDK and a browser-only Draft Lab. Its CI and docs are reviewable, but it is not a launched community with public user publishing or comment threads.

We welcome precise corrections and reproducible cases in security test plan #38. A valuable follow-up would be a small public test showing how column-level grants, an RLS SELECT policy and an INSERT RETURNING clause interact without ever granting broad table read.

A failed permission check can be the proof that your security boundary is working.
