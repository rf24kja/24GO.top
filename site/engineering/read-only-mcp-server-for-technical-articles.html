How to expose published technical articles to AI agents with a read-only MCP server

Giving an AI agent access to an article collection is useful only when the access boundary is unambiguous. For the first 24GOTOP integration, we deliberately exposed public, reviewed technical writing through a local MCP process—without granting an agent a database connection, a publishing credential, or even an arbitrary file path.

By 24GOTOP Engineering · Merged implementation PR #116 · Runnable source · Process and security tests

Release boundary: This is a local, read-only MCP server. It is not a remotely hosted MCP endpoint, verified AI-agent login, autonomous publishing workflow, or production community API. Hosted account-based publishing remains blocked on independent security review and database recovery proof.

Why not point agents directly at our application database?

The source-backed engineering archive already ships published HTML, RSS and a generated JSON Feed. Its content is intended for anonymous readers. Exposing those reviewed artifacts is much simpler to reason about than constructing an agent privilege model around unpublished drafts, author identity, moderation decisions or future personal data.

Our public MCP PR #116 chose a stdio transport: a compatible local host explicitly starts a Node.js process and exchanges JSON-RPC messages over its standard input and output. The server itself performs no network fetches, does not load environment credentials, and does not connect to PostgreSQL or Supabase. An authorized host must decide whether, when and how to start that executable.

The corpus is an allowlist, not a file browser

The server reads only three types of repository-owned artifacts: the committed engineering JSON Feed, the static full-text search index, and HTML pages identified by canonical URLs already present in that feed. Before returning a record, loadPublishedCorpus() checks the index version, matching article counts, duplicate paths, and a strictly shaped article filename. A URL does not become an allowed read target merely because a tool caller supplies it.

const origin = 'https://24go.top/engineering/';
const file = item.url.slice(origin.length);

if (!item.url.startsWith(origin) ||
    !/^[a-z0-9-]+\.html$/.test(file)) {
  throw new Error('Noncanonical article reference');
}

The actual implementation also verifies the corresponding indexed file and disallows duplicates. This exact-match design prevents requests such as file:///etc/passwd, path traversal, and external domains from being converted into arbitrary reads. Importantly, a local MCP client does not receive a generalized filesystem or shell tool.

Three intentionally small tools

list_articles returns published titles, canonical URLs, language, summary and date. search_articles looks through reviewed titles, summaries and indexed body text; it accepts a bounded keyword and a maximum result limit. read_article requires an exact public canonical URL and returns a plain-text representation of that published article. A client can also enumerate and read the same approved articles through MCP Resources.

Tool input schemas reject extra fields and restrict lengths and result counts. Search is not a semantic ranking service: it is deterministic case-insensitive substring search over a committed static index. That simplicity makes the observed result straightforward to verify, but it is not a promise of advanced retrieval quality or remotely accessible discovery.

Run the actual implementation

Clone the public source and use Node.js 22 or newer. No API key, paid model account or production database is required for the local article server:

git clone https://github.com/rf24kja/24GO.top.git
cd 24GO.top
npm run check
npm test
npm run mcp:articles

The last command starts a stdio process intended for an MCP-capable host, not an HTTP server that opens a web page. Follow the local client configuration guide for the right executable path and working directory. The process emits JSON-RPC protocol frames to stdout; regular diagnostic chatter must not corrupt that channel. Host-specific setup and real third-party host interoperability still require separate verification.

How we tested the boundary

The Node integration suite starts the real child process, sends a modern MCP server/discover request, lists tool definitions, invokes an actual list operation, and exercises compatibility with older client initialization. It tests search_articles using a phrase found in a published article body, then checks that the returned URL is one of the approved articles and that read_article can retrieve its text.

Negative tests try arbitrary URLs, traversal, unknown methods, malformed input, oversized queries and a fictional publish_article tool. Those requests cannot obtain private content or cause a write through this MCP surface. The protocol implementation supports the 2026-07-28 discovery path and a legacy initialization route. These are tested source-level properties, not evidence of remote deployment or an independent audit of every possible MCP host.

Untrusted content remains untrusted after retrieval

An article can contain code snippets, third-party quotations and potentially misleading instructions. We expose it as plain reference text with its source URL; a consuming AI agent should still treat retrieved article text as data, not as higher-priority operating instructions. Source allowlisting is necessary, but it does not make every statement within a technical article correct or safe to execute.

Separately, the public/private architecture boundary keeps future author accounts, moderation controls and hosted business logic outside this public MIT code path. In the release train, independent reviewer approval, real provider-signed authors, row-level security isolation and recoverable backups remain gates before any write permission can be added.

What developers can reuse

Start with already reviewed public documents, keep the approved corpus explicit, make tools read-only by construction, validate the exact identifier rather than trusting supplied paths, and test a real protocol process—not just helper functions. If the product later requires authenticated agent publication, design it as a separate service with identities, authority boundaries, budgets and moderation rather than quietly expanding this anonymous reader.

See the MCP source, executable regression tests, merged PR, and public progress record. Feedback on client compatibility and threat models is welcome through the repository issues. No public user article publishing has been launched as a result of this integration.
