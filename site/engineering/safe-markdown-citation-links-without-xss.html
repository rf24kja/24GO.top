How to render Markdown citation links without introducing XSS

A technical article needs hyperlinks to repositories, standards and documentation. But a user-supplied Markdown link can contain unexpected schemes, HTML-like labels and credentials embedded in a URL. We extended the browser-only 24GOTOP Draft Lab to support a deliberately small link syntax and tested the failure cases first.

By 24GOTOP Engineering · 30 October 2026 · Merged PR #78 · Regression tests

Scope: this is a limited author-side preview, not a general-purpose CommonMark implementation or a public publishing backend. It does not support embedded images, rich HTML or arbitrary URL schemes. No user-generated content is sent to the server.

What should a citation link accept?

Our initial preview treated all Markdown syntax as plain text, an intentional safety-first choice documented in the original DOM preview design. Later, authors needed references in the text they were writing. We chose a narrow [label](https://example.org/path) syntax instead of permitting arbitrary HTML.

The preview recognizes a bounded link label and URL. The target must be an actual HTTP or HTTPS URL with a hostname, without embedded usernames or passwords. Parentheses, backslashes, whitespace and nested Markdown are excluded from the supported form. Unsupported syntax remains visible as text; the parser does not attempt to repair it into a risky link.

Validate the URL before creating an anchor

The public renderer includes a dedicated URL gate. It uses the platform URL parser and then checks the exact protocol, hostname and credential fields:

export function safeCitationUrl(raw) {
  if (typeof raw !== 'string' || raw.length > 1500) return null;
  try {
    const url = new URL(raw);
    return ['https:', 'http:'].includes(url.protocol) &&
      url.hostname && !url.username && !url.password &&
      url.href.length <= 2048 ? url.href : null;
  } catch { return null; }
}

Do not rely only on a string prefix such as startsWith('http'). Scheme-like strings and unusual URL syntax are easy to misread. The normalized URL object gives you explicit components to check. The restrictive Markdown tokenizer further rules out input shapes we have not chosen to support.

Build DOM nodes, never concatenate untrusted HTML

For every accepted link, the editor creates a fixed a element, sets its visible label with textContent and its validated destination with setAttribute. The renderer does not interpolate the raw label into an HTML string or assign user content to innerHTML.

const link = document.createElement('a');
link.textContent = label;
link.setAttribute('href', safeUrl);
link.setAttribute('rel', 'noopener noreferrer ugc');
link.setAttribute('target', '_blank');
link.setAttribute('referrerpolicy', 'no-referrer');

Those attributes address different concerns. noopener prevents a new page from controlling its opener; noreferrer and the referrer policy limit referral information; ugc describes the link as user-generated. None of these makes a malicious external website trustworthy. A reader still chooses whether to follow it.

The page's surrounding text is added as text nodes. Inline code and fenced code are treated separately, so an author can discuss a malicious URL or show a code sample containing Markdown syntax without accidentally creating a link in the preview.

Adversarial test cases worth keeping

Our tests exercise meaningful security cases: a Markdown label resembling an image with an event handler; a javascript: destination; credential-bearing https://user:password@host URLs; and link-looking syntax inside a code fence. When the parser rejects a link, the text stays noninteractive, and no unsafe anchor is created.

The companion formatting tests verify that the editor's Link button wraps a selected single-line label, highlights a placeholder HTTPS destination for editing, and rejects oversized or multiline selections without losing the original article body.

This is a testable design contract, not an assertion that every possible Markdown or URL edge case is covered. In a hosted publishing platform, additional controls would include strict content security policy, vetted rendering libraries, moderation decisions, safe external redirects where needed and real-browser adversarial testing.

Why this matters for technical SEO and AI citations

Original technical documentation should make sources inspectable. A real hyperlink lets a human or browsing assistant follow the cited specification, GitHub PR or regression test. A visible source title without a usable link is harder to independently verify, but a link is valuable only if it is safely represented and not an implied endorsement.

Google's official AI-search guidance emphasizes crawlable, useful visible content and ordinary SEO fundamentals. It does not promise AI-feature placement merely because a page has links, special AI markup or an optional text index. We use explicit links for reader utility and provenance, not to simulate authority or engineer artificial backlinks.

How to reproduce the implementation

  1. Review public PR #78 for the DOM rendering and URL-validation changes.
  2. Clone the repository, run npm run check and npm test on Node.js 22+, then inspect the exact safe/unsafe test cases.
  3. Try the browser-only Draft Lab: highlight some technical text, choose Link, replace the destination with a real HTTPS documentation URL, and inspect the preview.
  4. Compare the old text-only preview rationale with the new allowed syntax. A new feature should extend a reviewed trust boundary deliberately, not accidentally.

Bottom line: treat Markdown links as untrusted input, constrain what you parse, validate normalized URLs, create only fixed DOM nodes and test rejected syntax as seriously as successful links. That approach is useful beyond 24GOTOP—to documentation editors, issue trackers and developer knowledge tools.

Primary evidence: PR #78, live source, security tests and independent HTTPS delivery check. The community publishing backend remains pre-launch.
