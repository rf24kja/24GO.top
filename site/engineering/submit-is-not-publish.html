Submit for review is not publish

In a technical knowledge community, the most dangerous shortcut may be treating a successfully submitted article as a successfully published one. We are separating those states before inviting people to trust the platform with their work.

24GOTOP engineering · Public security test plan #38 · Draft Lab author pilot #29 · OSS/hosted-core boundary

Release status: 24GOTOP is not a live community publishing service. The public repository contains an MIT-licensed local prototype and a browser-only Draft Lab. Private staging work on author-owned drafts and review intake is not deployed publicly; real two-user Auth/JWT verification, moderator MFA/identity binding, full publication transactions, and backup/restore are still open gates.

What can go wrong between Save and Publish?

Consider two people editing separate posts. An API accepts a JSON body with an author ID, and a queue consumer copies it into a moderation table. The queue reports success, but the author ID was never checked against a signed session. A subsequent moderation decision changes an internal status without creating a durable public article. The interface might report "published" even though nothing can be read at a stable URL.

These are not hypothetical capabilities we are claiming to have discovered in other products; they are failure cases we want our own project to reject. An author deserves more than a green HTTP status code.

Model the lifecycle as distinct trust boundaries

  1. Draft ownership: the server validates a current identity and proves that the user owns the specific draft. A client-supplied author label is not sufficient.
  2. Immutable submission: submitting version n must preserve the exact reviewed title, locale, source and full body even if the author later edits version n+1.
  3. Idempotent intake: retries or two concurrent workers must not create two moderator tasks for the same submission. A failed database step must roll back its dependent changes.
  4. Moderator authorization: only a verified, current, appropriately privileged moderator may approve or reject; their identity must be bound to the database decision and its audit record.
  5. Atomic public release: approved content, its source submission status, a durable public body/permalink and moderation audit must agree in one transaction. A queue status alone is not a public article.
  6. Reader safety: article text is untrusted. Rendering, links, localization and embedded code need a reviewed policy before the URL is safe for readers.

A small example: why a retry key matters

Suppose the same review task is delivered twice following a network timeout. If each attempt generates a new moderation post ID, one author may receive two conflicting decisions. Our proposed invariant is a one-to-one mapping from an immutable submission_id to a single moderation item, protected by database uniqueness and a single transactional operation.

submission A, version 3
  → stable review identity A
  → at most one moderator intake record
  → authenticated decision + audit
  → one durable public revision (not implemented)

A second worker should return the existing intake identity instead of silently duplicating it. If inserting the mapping fails, any associated moderator-queue insert should roll back as well. These behaviors are meaningful only when tested under actual concurrent transactions, not just mocked HTTP responses.

Source-level tests for private intake proposals have been exercised in disposable PostgreSQL 17 CI. This is evidence of the isolated SQL design, not evidence that any consumer is running, real accounts were used, or production publishing works.

What is publicly reproducible today?

The public 24GOTOP repository offers an independently testable local Node.js prototype, an experimental JavaScript SDK and a browser-only writing interface. The Draft Lab origin story explains why we did not connect an unfinished identity system to public writes; our Markdown preview security note shows one safe way to display article-like content without executing the author's HTML.

git clone https://github.com/rf24kja/24GO.top.git
cd 24GO.top
npm run check
npm test
npm run dev

The repository's read-only SDK example can be run separately with npm run demo:read. An empty local feed is expected; it is not a claim of successful real-user onboarding.

What we will not claim yet

  • No announced "launched" service, public writer accounts, uploaded articles, functional comments or permanent user-facing article URLs.
  • No signed, live two-user cross-account proof merely from SQL tests that simulate claims.
  • No production moderation security assurance while actor binding and staff MFA remain unverified.
  • No public read permission to internal staging schemas, admin tables or source submissions.
  • No adoption numbers, fabricated testimonials, artificial stars or auto-generated community comments.

See the public cross-user and race-condition test plan for specific security questions. The official founder-led hosted core is developed separately; public MIT-covered code retains its existing license and independent fork rights.

Three focused requests for feedback

We are looking for engineers who can help us answer concrete questions: Should a revised article require a brand-new moderation decision? What rejection/audit information should an author see without exposing moderator identity? And what is the simplest multilingual permalink strategy that preserves attribution and correct canonical URLs?

Join the existing security Issue for reproducible security test cases, or the voluntary Draft Lab pilot to test writing UX. Comments should describe actual observations or proposed acceptance criteria—not promotional replies or synthetic feedback.

Trustworthy publishing is not the speed of a button. It is the guarantee that a draft, a reviewer decision and a public page all mean what their labels say.

Verified public sources: project status, roadmap, test plan. Private source-level work is distinguished from live system evidence. Page availability on the website must be checked independently after deployment.
