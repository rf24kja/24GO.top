How to fix mobile horizontal overflow with real Chromium layout tests

A mobile site can look like it has a broken right-hand menu when the entire page is actually wider than the viewport. We reproduced this on the open 24GOTOP site, fixed the intrinsic layout constraints, and added headless Chromium checks so the same class of regression fails public CI.

By 24GOTOP Engineering · 11 November 2026 · Source fixes PR #189, PR #190 and PR #191

Evidence boundary: the verified results below are from real automated Chromium source-layout checks and public GitHub Pages release logs. They do not prove that a human tested every physical Android or iOS device, that search engines indexed the page, or that the pre-launch site offers hosted accounts or community publication.

Reproduce page-level overflow before choosing a fix

In the old header, six navigation links used white-space:nowrap in a flex row. The parent moved to a full-width second header line at narrow breakpoints, but its contents were still not allowed to wrap. In an isolated Chromium reproduction of the original header CSS, a 320 CSS-pixel viewport produced a 526-pixel-wide document; at 768 pixels, document width reached 914 pixels. The page itself could slide to the right, not just the menu.

Inspect the layout viewport, not the physical device pixel count. Run this in browser DevTools on a representative page:

const width = document.documentElement.clientWidth;
const page = Math.max(
  document.documentElement.scrollWidth,
  document.body.scrollWidth
);
console.log({ width, overflow: page - width });

Any positive difference merits investigation. A wide <pre> can be intentional if its own container scrolls horizontally; a document-wide scrollbar is not. Find the offending nodes with their bounding rectangles and inspect computed min-width, white-space, grid tracks and flex wrapping before changing overflow policy.

Fix the intrinsic width, not the symptom

The public header correction uses a grid with minmax(0,1fr) tracks and permits the text inside each navigation item to wrap. It offers three columns at tablet widths and two columns on phones. Navigation remains in normal DOM order and all links keep a minimum 44-pixel touch target. This is different from clipping the page.

@media (max-width: 1120px) {
  .site-header .header-inner > nav {
    display: grid;
    grid-template-columns: repeat(3, minmax(0, 1fr));
    width: 100%;
    min-width: 0;
  }
  .site-header .header-inner > nav a {
    min-height: 44px;
    min-width: 0;
    white-space: normal;
    overflow-wrap: anywhere;
  }
}
@media (max-width: 520px) {
  .site-header .header-inner > nav {
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}

The exact released selectors and responsive spacing are in landing.css. Do not apply global overflow-x:hidden as a substitute: it can conceal inaccessible content, focus indicators and genuine layout regressions. A code block or wide table can scroll locally without moving the document horizontally.

Test localized pages independently

Fixing the English menu was not sufficient. A subsequent real Chromium run found that the German homepage still widened to 418 pixels at a 320-pixel viewport. The culprit was a different mobile grid: a long localized roadmap heading increased the intrinsic width of a 1fr track. This was caught by the public PR #191 test, not by guessing from English screenshots.

The separate correction uses grid-template-columns:minmax(0,1fr) for that narrow track, constrains children, and uses overflow-wrap:anywhere on long headings. It retains the full German text; no translation is shortened just to fit a test. Similar checks matter for Thai, Russian, Portuguese and Chinese because scripts and word-breaking behavior differ.

Fail public CI on real browser dimensions

A static assertion that the stylesheet contains flex-wrap or a breakpoint does not prove the rendered document fits. We added a dependency-free Chromium DevTools Protocol smoke test using the checked-in HTML and CSS. It measures scrollWidth after layout for eight localized homepages and six important interior pages at seven viewport widths: 320, 360, 375, 390, 430, 768 and 1024 pixels.

That produces 98 layout combinations. The first run failed and identified the German page with a wider document. After the targeted change, the public CI recorded 98 passing Chromium layouts. A later post-merge CI run passed the same suite. The source and diagnostic output are available in check-mobile-layout.mjs.

# Run on a workstation with Chromium/Chrome and Node.js 22+
CHROME_BIN=/path/to/chrome npm run mobile:check
npm run check
npm test

The smoke test measures source-rendered markup and styles. It intentionally does not assert a working authenticated session, script-powered navigation, or touch interactions in Safari. A real-device accessibility pass remains a separate acceptance gate.

Prove that the corrected CSS reached HTTPS

Passing CI on source code is not proof that a content delivery network serves that revision. Public PR #190 extended the existing read-only HTTPS audit to compare eight CSS assets with the checked-out release source, not just HTML and JS. On the reviewed mobile fix, the public GitHub Pages release verified a matching commit/run receipt and 48 exact static files. Both the source-layout check and the postdeployment byte check are necessary evidence.

This release verification is specific to the public static site; it never uses private 24GO.online workflows, credentials or hosted production data. GitHub Actions are permitted only for this public repository under the current founder directive. The stronger gate demonstrates that the expected CSS was delivered at the time of the audit, not continuous uptime or search indexing.

A reusable mobile-release checklist

  • Measure whole-document width at 320, 360, 390, 430, 768 and 1024 CSS pixels; identify the element widening the page.
  • Check navigation labels, the longest localized headings, grids, forms, illustrations, footers and focusable elements.
  • Keep all links keyboard-accessible with visible focus and sufficiently large touch targets; never hide clipped menu items to silence a test.
  • Distinguish intentionally scrollable code/table containers from a page that drags sideways.
  • Run browser layout tests, then independently verify the exact deployed CSS and canonical HTTPS route.
  • Retest manually on physical iOS and Android, including dynamic UI and accessibility, before claiming full device coverage.

The public repository includes a mobile QA procedure. For the more general principle of release proof, see how to verify a deployed GitHub Pages release. The work does not turn a browser-only Draft Lab into an authenticated publishing system.
