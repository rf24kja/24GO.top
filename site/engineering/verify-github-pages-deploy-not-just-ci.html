How to verify a GitHub Pages deployment—not just a green CI badge

A successful pull request confirms the repository changed. A green deployment action confirms a deployment workflow completed. Neither proves a reader can fetch the correct HTML and JavaScript from your canonical domain. We learned this during a real 24GOTOP release and turned the failure into a reproducible deployment check.

By 24GOTOP Engineering · 30 October 2026 · HTTPS verification PR #79 · Race fix PR #82

What was verified: the public static pages and assets were fetched over HTTPS from https://24go.top by GitHub-hosted runners. No measurement here proves constant uptime, Google indexing, production accounts, or a live user publishing API. This site is still pre-launch.

The three different questions you must answer

  1. Is the code correct? Unit tests, linting, build checks and source review can show the intended content and behavior under test conditions.
  2. Did deployment finish? The official GitHub Pages workflow reports whether uploading and publishing the static artifact succeeded.
  3. Is the actual site serving the update? An independent request must fetch the canonical HTTPS URL, follow safe redirects and inspect the resulting HTML/JS files for a release-specific, truthful marker.

These are separate observations. A deployment can finish before a CDN edge serves new content; a test can also run before the deployment finishes. Reporting “launched successfully” after a Git merge alone conflates all three.

What happened in the 24GOTOP release

Our public eight-language Draft Lab change merged into the MIT repository. The source CI passed and the Pages deployment succeeded. The first external smoke check, however, failed: the check ran on push while the public site still served the previous version, so the new interface-language selector was absent.

A later smoke check triggered by the completed Pages workflow passed. That is stronger delivery evidence, not proof that the earlier failure was imaginary. The failure reflected the real state visible to the runner when it executed. We retained both run links in the deployment evidence log.

Fix the dependency, not the assertion

The solution in PR #82 was to remove the direct push trigger from the live verification workflow. It now runs after successful completion of Deploy pre-launch landing, or by explicit manual dispatch. The workflow itself needs only read access to the checkout; it cannot publish or change site settings.

name: Verify live Draft Lab release
on:
  workflow_run:
    workflows: ["Deploy pre-launch landing"]
    types: [completed]
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
jobs:
  verify:
    if: github.event_name != 'workflow_run' || github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - run: bash -n scripts/check-live-draft-lab.sh
      - run: bash scripts/check-live-draft-lab.sh

The snippet illustrates the reviewed workflow shape; consult the current workflow source for the exact maintained version. Merely waiting a fixed number of seconds on every push is less reliable than waiting for the deployment event itself.

A practical, read-only HTTPS smoke test

Our public test script downloads the canonical homepage, the experimental editor HTML, and its browser JavaScript. It restricts redirects to HTTPS, uses bounded timeouts and retries, and verifies that specific expected artifacts and safety messages are present. It does not upload content, authenticate, print response bodies or access any confidential user data.

curl --fail --silent --show-error --location \
  --proto '=https' --proto-redir '=https' \
  --connect-timeout 10 --max-time 25 \
  --output draft.html https://24go.top/draft-lab.html

grep --fixed-strings 'id="uiLocale"' draft.html

This example checks whether the latest deployed page contains the separately controlled interface language selector. The real script also checks that the preview still protects external links and that the page honestly says it is not public article publishing. Assertions should be based on stable user-facing behavior rather than brittle implementation-specific whitespace or minified line numbers.

To avoid reporting a success for a mismatched release, make your check look for at least one feature unique to the revision being deployed. For more critical deployments, verify the deployed version identifier and content digest, and audit cache headers and redirects. A smoke test is not a substitute for real-browser navigation, accessibility tests or a production rollback drill.

SEO and AI discovery need delivery evidence too

Search engines and browsing agents are clients of the published site—not of your GitHub repository. A complete sitemap only helps if its URLs actually return readable HTML over HTTPS. Verify robots.txt, sitemap.xml, RSS and representative article pages separately after release.

Google explains that satisfying its technical requirements and having discoverable content does not guarantee indexing or AI-feature inclusion. For actual search performance you still need verified Search Console and Bing Webmaster Tools properties, not estimated traffic or a site: query treated as a definitive index count.

Copyable checklist for your next static release

  • Review the exact commit and run project CI before merging.
  • Deploy only the expected static artifact with least-privilege GitHub Actions permissions.
  • Wait for the Pages workflow success event before checking the live URL.
  • Fetch canonical HTTPS pages from an external runner with safe redirects and retries.
  • Assert a release-specific feature and the site's real public-security/disclosure boundary.
  • Keep both failed and successful run links, and distinguish delivery from indexing, usage or conversion.

This process is intentionally inspectable: PR #79 added the smoke, PR #82 corrected scheduling, and the live verification run records a successful externally fetched result. For the related search checklist, see publishing technical articles for people and AI search.
