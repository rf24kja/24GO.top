How to safely bound public GitHub API article proposals

A public article proposal board needs to remain responsive when an upstream API returns an oversized body, malformed JSON or unexpectedly shaped issue data. Our public 24GOTOP contribution interface reads GitHub issues without granting browser visitors a publishing credential. In PR #179 we hardened that read boundary and protected already loaded proposals from a failed refresh.

By 24GOTOP Engineering · 10 November 2026 · Merged source PR #179

Scope: this is a static, read-only browser interface over public GitHub issue metadata. It is not authenticated user publication, a moderated PostgreSQL service or a hosted agent API. Search-engine indexing and real-user uptake are not claimed.

Why read-only responses still need budgets

A network response can have a successful status without containing safe, bounded JSON. Directly calling response.json() delegates memory and parsing work to a body with no application-controlled byte ceiling. Oversized responses can consume unnecessary memory, and malformed data can leave the interface in an inconsistent state. This is an availability and data-integrity problem even though the endpoint exposes public information.

We use a 256 KiB limit on GitHub issue metadata response bodies, enforced as bytes arrive. A size check performed only after response.json() would be too late. HTTP status and media type checks, deadlines, unexpected redirects and response shape validation are separate concerns, and all matter in a robust client. Exact behavior should be checked in the maintained source and its regression suite.

A minimal bounded-streaming pattern

The illustrative function below rejects a response after its accepted byte budget is exceeded. It is not a drop-in production fetch client: a deadline, redirect restrictions and schema checks must surround it. Importantly, it reads bytes before decoding and parsing the final JSON document.

async function parseLimitedJson(response, maxBytes = 256 * 1024) {
  if (!response.ok || !response.body) throw Error('Unavailable');
  const reader = response.body.getReader();
  const chunks = [];
  let length = 0;
  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      length += value.byteLength;
      if (length > maxBytes) throw Error('Response too large');
      chunks.push(value);
    }
  } finally {
    await reader.cancel().catch(() => {});
  }
  const bytes = new Uint8Array(length);
  let offset = 0;
  for (const chunk of chunks) {
    bytes.set(chunk, offset);
    offset += chunk.byteLength;
  }
  return JSON.parse(new TextDecoder('utf-8', { fatal: true }).decode(bytes));
}

After parsing, treat data as untrusted: validate the array length and each accepted issue field. Render external issue titles as literal text rather than injecting them as HTML. When a transport or validation error occurs, show an explicit error state instead of pretending that an empty result proves the repository has no proposals.

Do not discard valid results on refresh failure

The second principle in the reviewed patch is to preserve previously loaded and validated proposal cards if the next network request fails. A failed refresh should not turn a populated browsing experience into an empty page. On the first-ever request, however, there may be no valid cached result, so the interface should show an error and offer retry rather than falsely claim there are zero matching proposals.

This distinction makes the browser interface useful under real mobile-network faults. It also keeps stale data and unavailable data from being misrepresented as verified fresh results. Public GitHub issue metadata can change, and this interface does not guarantee that a previously observed issue remains open at any later moment.

Negative cases worth testing

  • Valid public JSON succeeds under the size ceiling and yields only accepted fields.
  • Unexpected JSON types, malformed UTF-8, malformed JSON and response errors fail closed.
  • An oversized streaming payload is refused before whole-body parsing.
  • Network failures and invalid follow-up pages do not erase previously rendered valid proposals.
  • Issue titles and summaries are treated as external data, not executable markup.

These are useful boundaries for a GitHub issues integration, not evidence that the entire publishing product is launched. The public review and implementation establish the source changes, while a separate GitHub Pages delivery verification is required to show that the released static client reaches readers over HTTPS. CI success alone does not establish CDN delivery.

The broader editorial boundary

24GOTOP's hosted author-to-publication path remains a distinct product milestone requiring authenticated identities, auditability, moderation, PostgreSQL transactions, RLS and tested recovery. The public proposal board neither bypasses those gates nor claims to solve them. Its useful job today is to safely display external suggestions and let contributors participate through GitHub.

We welcome review of this exact implementation and its edge cases, without collecting draft content or private credentials. Developers can also experiment with the browser-only Draft Lab while that hosted workflow is not available.

Primary evidence: merged PR #179, public source, and tests. No invented users, traffic or deployment claims.
