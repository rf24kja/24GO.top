Prevent API key leaks in JavaScript SDKs: why HTTPS alone is not enough

A developer client can support remote read requests and still carry a dangerous local-only write token. If the same client blindly attaches that token to any configured base URL, a perfectly valid HTTPS request can deliver the credential to the wrong server. We found and closed this boundary in the open-source 24GOTOP JavaScript SDK prototype.

24GOTOP engineering · Merged fix PR #56 · Actual SDK implementation · Negative security tests

Scope: this article describes a local developer prototype and its reviewed source tests. The 24GOTOP hosted publishing platform, verified production sessions and remote write API are not launched. No real API keys, customer data or private backend modules appear here.

The failure mode: an innocent-looking remote URL

Imagine a development SDK that defaults to http://127.0.0.1:3000 and accepts an apiKey for a temporary publishing demo. The SDK also accepts a customizable baseURL, because developers may eventually query a remote read-only API. An accidental configuration change to https://some-service.example must not cause a demo publishing token to travel to that address.

HTTPS authenticates the TLS endpoint and encrypts transport. It does not establish that the endpoint is authorized to receive a particular credential. The question is not simply “Is this URL secure?” but “Is this the intended recipient of this specific token?”

In the 24GOTOP prototype, TopClient.listPosts(), getPost() and health() are read operations. publishPost() is different: it attaches a bearer token for a local JSON demo. Before the fix, a user-configured HTTPS remote origin was an unsafe destination for this local credential.

The first rule: validate the base URL structurally

The constructor parses the configured URL with the standard JavaScript URL class. It refuses non-HTTP(S) schemes, embedded usernames/passwords, query strings, fragments and non-root paths. This removes several ambiguous or misleading input forms, but it does not by itself establish that a remote server is an approved destination for the write token.

const parsed = new URL(baseURL);
if (!['http:', 'https:'].includes(parsed.protocol) ||
    parsed.username || parsed.password ||
    parsed.search || parsed.hash ||
    parsed.pathname !== '/') {
  throw new TypeError('Invalid API base URL');
}

Compare parsed hostnames, not strings such as baseURL.startsWith('http://127.0.0.1'). The lookalike domain 127.0.0.1.evil.example begins with those characters but is not the loopback address. Similarly, a hostname containing “localhost” is not necessarily localhost.

Keep a local development token local

For this prototype, we explicitly allow the development write credential only when the parsed destination hostname is one of three loopback names: localhost, 127.0.0.1 or IPv6 loopback [::1]. Every other hostname fails before any fetch operation can run.

const hostname = new URL(this.baseURL).hostname;
const loopback = ['localhost', '127.0.0.1', '[::1]'];
if (!loopback.includes(hostname)) {
  throw new TopClientError(
    'Refusing to send a LOCAL development publishing key'
  );
}

This guard belongs directly in publishPost(), not merely in a README warning. It allows remote read-only experiments without sending the token, while protecting the operation that would attach Authorization: Bearer ....

There are additional layers: the SDK sets redirect: 'error' for requests so a fetch implementation does not silently follow a redirect to another origin. The local demo server separately restricts write requests to a verified loopback socket and validated Host/Origin requirements. Each protects a different part of the boundary; none should be replaced by a convenient shared secret in production.

Reproduce the rejection without making a network request

The easiest test is not to send a fake token to a remote test server. Inject a fetch implementation that counts invocations, then assert the remote write is rejected before it is called.

import assert from 'node:assert/strict';
import { TopClient } from './packages/sdk/index.mjs';

let calls = 0;
const client = new TopClient({
  baseURL: 'https://api.example.org',
  apiKey: 'LOCAL_TEST_VALUE_ONLY',
  fetchImpl: async () => {
    calls += 1;
    throw Error('Should never be called');
  }
});

assert.throws(
  () => client.publishPost({ title: 'Example' }),
  /Refusing to send/
);
assert.equal(calls, 0);

This uses an artificial value, not an active credential. The actual SDK test suite also rejects remote HTTP and HTTPS origins, private LAN addresses and lookalike hostnames, while confirming that unauthenticated remote reads and legitimate local publishing calls still behave according to their intended contracts.

To reproduce the public source tests, clone the repository and use Node.js 22 or newer:

git clone https://github.com/rf24kja/24GO.top.git
cd 24GO.top
npm test

These assertions verify a source-level recipient guard and the injected fetch boundary. They do not certify the underlying operating system's DNS configuration, a future reverse proxy, or a production authorization scheme.

Four additional things an SDK security review should ask

  1. Who owns the key? A shared local development token is not a production account identity. Browser-visible credentials, user-owned API keys and server-held secrets have different storage and delegation rules.
  2. Can redirection change the recipient? Redirect following can move a request beyond an initially approved origin. Require a deliberate policy and tests for redirect behavior, not an accidental default.
  3. What happens on cancellation? A pre-aborted operation should not issue a request. Error messages should not echo arbitrary abort reasons that might contain sensitive values. The SDK tests these cases separately.
  4. Does the server independently enforce scope? A client guard can be bypassed by a custom script or another SDK. The receiving API must authenticate and authorize the caller independently; local demo checks cannot replace user-specific production Auth.

What we changed, and what remains unfinished

The relevant fix is publicly reviewable in PR #56. It prevents the 24GOTOP SDK's publishPost() path from transmitting its local development key to remote hosts and preserves read-only requests without the publishing token. GitHub CI and targeted Node tests passed for that change.

We deliberately have not presented this as a complete production SDK. Real 24GOTOP publication still requires verified user sessions, scoped grants, database row ownership, moderation, an audit trail and independently tested backup recovery. A safe local client check does not make unreviewed public writes acceptable.
