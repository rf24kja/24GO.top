How to localize a Markdown editor without losing drafts

A writer may prefer a Russian interface while producing an English article, or switch to Thai controls halfway through editing. A language selector must not silently translate the document, change its metadata, or mark an unchanged imported file as modified. Here is a tested, source-backed approach.

By 24GOTOP Engineering · 30 October 2026 · Implementation PR #81 · Tests

Verified scope: the public 24GOTOP Draft Lab is an on-device writing prototype. It does not automatically save, upload or publish articles. Its translations are first-pass and still require native-speaker and screen-reader review. The hosted 24GOTOP community is not launched.

The trap: interface locale is not article locale

A single locale variable is tempting. But there are two different decisions: the language of buttons, hints and errors; and the language of the article readers will eventually see. Treating them as the same field can cause a UI preference change to rewrite exported metadata, invalidate a draft comparison or select an unintended publication language.

Our public editor keeps postLocale for the authored document and introduces uiLocale for display strings. Changing uiLocale should not modify the title, body, category, source URL, article locale, selection or previously reopened file baseline. A multilingual author can therefore work across languages without affecting the original writing.

Architecture: a fixed dictionary, not a document translation pass

The translation module has eight explicit dictionaries: English, Russian, Thai, Spanish, French, German, Portuguese and Chinese. Every locale uses the same set of keys. Missing or unexpected keys fall back to a known English string or are rejected by the lookup function.

// Simplified from the public implementation
const ui = key => uiText(uiLocale.value, key);
function refreshInterface() {
  applyUiLanguage(document, uiLocale.value);
  preview();
  message('');
}
uiLocale.addEventListener('change', refreshInterface);

The important part is what that handler does not do. It does not write to the draft fields, export a new file, make a network request or call a translation API. On the existing page, fixed markers such as data-ui="headline" identify interface text. Text nodes are updated via textContent, placeholders through setAttribute, and html.lang is set to the current interface locale.

This is much safer than accepting translated HTML fragments and assigning them to innerHTML. The article body is untrusted user content and remains separate from the interface dictionary. The dictionaries contain only fixed source-controlled strings, not rich text fetched from remote services.

Handle warnings and validation, not only button labels

Many incomplete localizations translate navigation but leave the most important text in English: this draft is not saved, opening a file replaces the current draft, download requested, or your selection is invalid. Those messages affect irreversible choices and should be localized with the rest of the UI.

In PR #81, the eight dictionaries include 78 keys each. They cover labels, editor controls, accessibility text, error states, import confirmations and privacy notices. The English text is present directly in HTML so the page has meaningful static content before JavaScript executes. This is a local application feature, not eight translated search landing pages.

Preserve the file baseline during a language switch

The editor supports a workflow in which a writer downloads an .md file and later reopens that exact exported file. It tracks the reopened file in a memory-only baseline. The warning before leaving depends on whether the current article actually differs from that baseline, not whether a user changed the interface labels.

// Conceptual invariant checked by the tests
const before = { title, body, locale, category, source };
changeInterfaceLanguage('ru');
assert.deepEqual(currentDraft(), before);
assert.equal(hasUnexportedChanges(currentDraft(), baseline), false);

The actual browser-simulation test reopens a locally exported Markdown file, changes the interface from English to Russian, and checks that every author field is unchanged. It then edits the body, confirms the unsaved-change guard becomes active, switches to Chinese, and checks that the guard remains active. This catches a class of data-loss bugs that dictionary-completeness tests alone cannot detect.

What about accessibility and SEO?

The interface-language selector has an explicit label and uses native select keyboard behavior. The page's lang attribute changes with the interface so assistive technology has an appropriate language hint. Accessible labels and placeholders use the same translation keys as visible controls. We have automated assertions for those contracts; we have not measured comprehension with native speakers or tested every device/screen reader.

From an SEO perspective, do not create eight duplicate URLs merely because a JavaScript control can switch the UI. Genuine locale-specific articles need unique, translated visible content, correct language URLs and self-consistent canonical/hreflang signals. This engineering note is an English original and declares lang="en"; the local editor itself remains noindex because it is a prototype, not a public document to rank.

Reproduce the evidence

  1. Inspect PR #81 and its changes to the dictionary, static HTML and on-device editor.
  2. Run npm test after cloning the public MIT repository (Node.js 22 or newer). Review dictionary completeness and the import-preservation test.
  3. Open the live Draft Lab. Draft a short technical explanation in English, change interface language to Russian or Thai, export the file, and confirm its content-language metadata still matches your selection.
  4. Check the post-deployment HTTPS smoke evidence. It shows the files were served; it does not prove native-language quality.

Practical checklist for any multilingual editor

  • Model UI language and document language separately.
  • Keep the translation surface fixed, source-controlled and reviewable; use safe text/attribute insertion.
  • Translate destructive confirmations, status and accessibility text as well as headings.
  • Test both unchanged and dirty drafts through multiple language switches.
  • Use real bilingual readers and assistive-technology users to validate wording and navigation before launch.
