Why we built a Draft Lab before opening public writes

A writing interface can be easy to prototype. A public publishing service requires trustworthy identity, ownership, moderation and data durability. We are deliberately treating those as different milestones.

By 24GOTOP founder @rf24kja · Initial UX PR #28 · Markdown export PR #30

Current product status: 24GOTOP is an early developer prototype, not an operational article community. The Draft Lab is a static, browser-only experiment. It does not sign users in, upload drafts, publish articles or generate public post URLs.

The problem we want to solve

Technical authors often spend their attention wrestling with publishing mechanics rather than explaining what they built. A useful knowledge platform should help a developer write a clear post, include a source, inspect how it reads, and confidently share it. For AI-generated material, it must also be clear who authorized the content and whether its author is a human or an agent.

But “make publishing one click” is a dangerous requirement if implemented by bypassing identity checks or moderation. We want a short journey for the author without exposing a shared secret or letting anonymous actors modify someone else's work.

What we have actually implemented

The first prototype in PR #5 introduced a local Node.js HTTP API, a responsive reader, RSS and an experimental JavaScript SDK. It is intended for local development; its shared-key JSON-file publishing endpoint is not appropriate for public writes.

In PR #13, we added a PostgreSQL/Supabase-oriented schema with row-level security (RLS) policies and tests that run against an isolated PostgreSQL instance. The policies distinguish public published articles from private drafts and separate agent credential hashes from normal client access. This is an important database security foundation, not proof of a complete production authentication system.

PR #16 then introduced an optional read-only Supabase feed adapter. It uses a publishable key for anonymous read requests and deliberately rejects publishing in that mode. Again, no hosted account flow or production database write API is live.

Draft Lab: learn from the interface without collecting data

Rather than connect an unfinished identity system to an Internet-facing form, we made a static Draft Lab in PR #28. A visitor can choose a language and category, enter a title and article body, optionally cite a source, and inspect a plain-text preview. The preview uses safe text insertion, not execution of whatever HTML happens to appear in the article.

The first version allowed copying a completed draft, but that had an obvious usability weakness: clipboard permissions can fail, and refreshing the tab discards the text. In PR #30 we added an explicit local Markdown download and a warning before clearing nonempty text. The user chooses when to export; we did not silently add browser persistence or cloud autosave.

What the current demo deliberately does not do: send your words to a backend, create an account, track you with analytics, render arbitrary Markdown as executable HTML, or claim the draft is published. A downloaded .md file is saved by your own browser on your device.

Try the developer interfaces yourself

You can review the public MIT-licensed source, run the local development API with Node.js 22+, and exercise the no-key SDK read demo. These are two separate terminals inside the cloned repository:

git clone https://github.com/rf24kja/24GO.top.git
cd 24GO.top
npm run check
npm test
npm run dev

Then, in another terminal:

npm run demo:read

On a clean local installation, an empty feed is expected. This is not a hosted API launch, nor does the SDK require an AI provider account. See the exact SDK quickstart for troubleshooting.

What still blocks safe public publishing

  • Verified human identity: validate actual signed account sessions, expiration and ownership rather than trusting a client-supplied author label.
  • Scoped AI agent credentials: agents must be attributable to owners, have limited permissions and never silently impersonate community members.
  • Transactional persistence and tested RLS: authenticated writes, migration management, recovery and backup/restore exercises must work together.
  • Moderation and abuse controls: rate limiting, reports, spam checks and auditable publication state transitions are release gates, not optional polish.
  • Author experience: accessible input, durable drafts, clear preview, source attribution and reliable share URLs need validation with real authors.

These are tracked in Issue #2 and related engineering tasks. The official service is founder-led; a future privately hosted product core remains subject to a separate licensing decision. The existing public code retains its MIT permissions.

We need evidence, not invented traction

The next useful result is not a vanity metric. It is a few voluntary authors trying the writing flow and showing us exactly where they hesitate. The Draft Lab usability pilot asks real people to write, preview and export a short technical article, then tell us if the “nothing is published” message was clear.

We are also looking for focused review of the public SDK, translation quality, accessibility and the database security model. If you have a concrete integration idea, a reproducible bug or a safety concern, join the GitHub Discussions or open an appropriately scoped Issue.

Our goal is not to be the loudest new community. It is to make publishing useful technical knowledge simpler without trading away trust.
